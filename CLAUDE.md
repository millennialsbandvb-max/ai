# MPC Live II custom firmware: handoff

This repo builds a custom firmware for the user's **Akai MPC Live II (Gen1, 32-bit ARM)**: their Hakai 3.10.0 image
(a modded MPC OS 3.10.0; earlier builds were on Hakai 3.9.1) plus open-source VST2 plugins with touchscreen pages, and a browser remote. MPC OS's built-in
JUCE host loads Linux VST2 `.so` files listed in `MPC.settings`; we install the plugins into the image and a boot
service adds their entries. All of it has been tested on the user's MPC.

## Working with the user

- **USB only.** They can't reach the MPC's shell, so every change ships as a **whole firmware image**, installed
  with the normal MPC USB update. They don't use SSH.
- **Deliver the whole image** (`MPC-3.10.0-Gen1-update.img`, ~196 MiB) with SendUserFile, plus its size and
  SHA-256: that works since the user moved to Max (Oct 2026). The 7 pieces `build_firmware.sh` also writes
  (`.part1` to `.part7`, under 30 MiB each, joined by the user) are the fallback if a whole-file send fails.
- **The Hakai original is not in the repo** (too big). It's in the user's Google Drive:
  https://drive.google.com/file/d/1VhMwT7Kt1D1Bia1Rm5BtfDJ2DOzDutO3/view (Hakai on MPC OS 3.10.0, 204,576,287
  bytes, SHA-256 `1776ae5e3a3eaa223e7242142c5ef10fc3cc4c4ded10599d76e9f7a6250dea9f`). Download with
  `curl -L -o MPC-3.10.0-Gen1-update.img "https://drive.usercontent.google.com/download?id=1VhMwT7Kt1D1Bia1Rm5BtfDJ2DOzDutO3&export=download&confirm=t"`
  (needs "anyone with the link" sharing; otherwise ask them to share it, or read it via the Drive connector).
  The older Hakai 3.9.1 (`1dP3Ftm3UFZw04n4BblGSErE9-G5D7HKL`, SHA-256 `e4428bb7…554d8a`) builds too.
- **Always send the firmware as soon as it's built and tested**, without being asked (the user's standing ask).
- They want short, plain answers; they decide workflows. NAM: **A2 models only** (A1 Standard is too heavy).
- Firmware images are never published to the public repo (only source); keep them in the scratchpad.

## Build everything

```
tools/build_firmware.sh <Hakai MPC-3.10.0-Gen1-update.img> <out dir>
```

About 6 minutes. It builds every plugin for ARM with its page, the remote, patches the image
(`nam-mpc/firmware/patch_image.sh`, which verifies the filesystem and reads every file back) and writes the 7 pieces.
Tools needed: arm-linux-gnueabihf-gcc/g++, cmake, ninja, qemu-arm, python3 + PIL, e2fsprogs, xz, upx, unzip.

## Changing plugins

- **Knob ranges/defaults/names:** NAM `PARAMS[]` in `nam-mpc/src/nam_mpc.cpp` (+ `params.json`); SFZ `PARAMS[]` in
  `sfizz-mpc/src/sfizz_mpc.cpp` (+ `page/params.json`); Dragonfly and Airwindows ranges come from the plugins
  themselves, labels/layout from their `pages.py`.
- **Screen layout:** `layout.conf` per plugin (Force Shadow syntax, see `mpc-vst-plugins-main.zip` tools). Previews:
  `build/preview_*.png` after `./build.sh skin`. A page folder must be named `<vendor> - VST - <plugin name>`.
- **Presets** are only knob settings the user dials in and saves on the MPC: no build needed.

## Testing (no hardware here)

- `./build.sh host` then the plugin's own test (`nam-mpc/build/nam-test-host`, `sfizz-mpc/build/sfz-test-host` with
  `SFZ_MPC_DIR`), or `tools/vst_test.c` for any plugin.
- ARM builds run under `qemu-arm -L <sysroot>`; `build_firmware.sh` leaves the image's libraries in `<out>/work/sysroot`.
- The browser remote has a PC build (`mpc-remote/server/build/mpc-remote-test`, `MPC_REMOTE_FAKE_BMP=<bmp>`).

## Hard-won lessons (don't repeat these)

- **Never open the display device (`/dev/dri/card*`) before MPC has it.** The first opener becomes DRM master and MPC
  then hangs on the logo. The remote opens it only while a browser watches, only once another process has it open,
  and drops master at once.
- **One NaN reaching MPC's mixer silences everything until restart.** Every plugin now cleans its input, resets
  itself if its output goes bad or past +36 dB, and caps output at +12 dB. Keep that in any new plugin.
- **sfizz bugs worked around in SFZ MPC:** a note-off on the same sample as its note-on is ignored, and notes starting
  on the same sample in a mono (`off_by`) instrument don't choke (chords hung). Notes are spaced one sample apart.
- MPC renames its process: find it by its open files, not by name.
- MPC's panel (buttons, pads) is MIDI from its internal controller's "private" port, which MPC opens as raw MIDI
  `hw:<card>,0,1`; there are no Linux input devices for it. The remote's buttons work by giving MPC an ALSA virtual
  raw MIDI input fed through the sequencer (as Hakai's driver does) and sending the learned button messages to it.
  `mpc-launch` stops loading it after 3 failed starts; the page has "Button input off". The virtual input must be
  opened as `virtual:MERGE=0`: the default leaves out repeated status bytes (running status) and MPC's panel reader
  then ignores everything (all buttons and pads dead).
- **Web In**: the remote page streams an audio file (16-bit stereo over the WebSocket, paced by the page) into a ring
  in `/dev/shm/mpc-webin` (`mpc-remote/webin.h`); `preload/webin.c` (in mpc-buttons.so) adds it to the chosen input
  pair inside MPC's `snd_pcm_readi/readn`, resampling with drift control (~0.2 s buffer). Browsers only allow mic/tab
  capture on https pages and the remote is http, so it's files only; the user declined AirPlay (shairport-sync).
- **MPC browser** (experiment): headless Chromium 150 (Debian 12 armhf) in `/data/mpc-browser`. Too big for the rootfs
  (~80 MB free; its partition size is unknown, so don't grow it) and cards are mounted noexec, so the firmware carries
  an installer instead: the page's Start (first time) runs `browser-install.sh`, which downloads the packages in
  `packages.txt` from deb.debian.org with `debfetch` (libcurl/libcrypto, SHA-256 checked) and arranges them exactly
  like `build_bundle.sh` (or unpacks `MPC-Browser.tar.gz` if one is on a card). mpc-remote starts it
  (`run.sh`, nice 10) and tunnels its DevTools at `/cdp/` (DevTools only accepts Host 127.0.0.1, ignores HTTP/1.0);
  the page shows a screencast and sends input. Its ALSA default is a `file` device piping to `webin-feed` (Web In).
  Not tested on the device yet: memory (~1.2 GB free beside MPC) and CPU are the open questions. No zram in the kernel.
